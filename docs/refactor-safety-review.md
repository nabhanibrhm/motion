# Refactor safety review

Review: ChatGPT / Codex, GPT-6.1 Terra, xhigh effort. Scope: voice generation and import, storage and staging, mastering, root dependency readiness, and retirement prerequisites. This is a code and evidence review; it is not visual or listening sign-off.

## Evidence checked

- Compared the SHA-256 of every legacy section MP3 with its per-episode imported copy: 46 of 46 match across all seven episodes. Compared every file in the seven legacy voice chunk caches with the corresponding imported copy: 721 of 721 match. These checks establish byte preservation at the time of review, not future availability if caches or archives are deleted.
- Two identical legacy chunk filenames were found with different audio content across episodes. Imported chunks are retained per episode; the revised Supertonic cache key includes the legacy content hash, preventing these different recordings from collapsing into one cache entry.
- `node --test tests/voice-storage.test.mjs` passed all four tests. The tests exercise synthetic import integrity and invalidation, path and lock rejection, scoped cleanup, and reference-based staging with a read-only check. They do not prove behavior under simultaneous real synthesis processes.
- `node scripts/motion.mjs sync inflasi --check` passed. The existing `docs/refactor-fidelity.json` reports 4,155 matching procedural samples across all seven episodes, including timeline and caption comparisons. That report explicitly does not verify browser pixels or encoded audio.
- A synthetic FFmpeg mastering integration used an eight-second H.264/AAC source and a separate sine-wave music bed. With and without the bed, output duration was 8.000 seconds, video stream SHA-256 matched the input, and audio was AAC at 48 kHz. FFmpeg ebur128 measured -14.0 LUFS in both outputs, with true peaks of -10.0 dBTP without the bed and -9.0 dBTP with it. The decoded audio hashes differed, confirming the bed affected the mix. The input file hash remained unchanged; a missing-bed failure preserved the prior output, and identical input/output paths were rejected. Artifacts are in `.cache/verification/mastering/`.
- The reviewed generator uses piped FFmpeg decoding, per-key synthesis locks, versioned alignment and pitch keys, and content hashes for imported voice recordings. The outer voice state includes narration, generator and dependency-lock hashes, manifest hash, and section-audio hashes. The shared staging implementation publishes a fresh asset snapshot and checks for changes without writing in check mode. Literal `F1.asset('assets/...')` references are now recognized.

## Outstanding limitations and operating constraints

- Browser rendering and visual comparison remain blocked by the environment's loopback access restriction. The procedural results cannot establish visual fidelity, media loading in Chrome, or correct final audio. Obtain snapshot and full fresh render review on a host where HyperFrames can serve its project before claiming render parity.
- Root `npm ci` has not been proven from a clean offline environment. The root Python environment was copied from an existing installation and reused offline; installation from the recorded lock files has not been independently demonstrated. Preserve a working recovery path until clean installation and the required voice/model dependencies have been verified on a suitable host.
- Asset staging detects literal paths. Computed asset names cannot be inferred reliably and must be declared in `config.assets`; add an explicit entry when authoring such scenes. The staging test checks literal helper references, not arbitrary dynamic JavaScript.
- Immutable staged assets may be hardlinked to their canonical source. Staging replaces entries without truncating them, but an external in-place edit of either hardlink changes both; update canonical assets by writing a new file and atomically replacing the source entry, and treat staged assets as read-only.
- The focused tests use synthetic fixtures. Real concurrent synthesis, cross-device hardlink fallback, and interrupted publication still need independent integration coverage. The mastering check covers a simple synthetic signal, not listening review, demanding peak material, failure partway through FFmpeg publication, or proof that every caller supplies fresh raw input. Cache locks fail safely when held, and a lock left by an interrupted process requires inspection.
- Rendering must use a unique fresh raw input and serialize operations on the same episode; master output must only be published after success. The CLI owner is implementing and testing those guards. The standalone `masterVideo` API itself checks that input and output differ but cannot identify an already-mastered input.

## Legacy retirement gate

The audio and chunk comparisons support preservation, but they do not by themselves authorize or validate bulk removal. Before retiring any specific old dependency tree, verify the exact bounded paths and current contents, the source archive and its hashes, all imported section and chunk hashes, and the root environment's required functionality again immediately before removal. Keep the migration baseline, imported voice caches, authored source archive, existing finished outputs, and any old renders outside that explicit cleanup scope. Avoid following links or junctions. The inventory records that dependency directories were counted but not content-hashed, so it cannot prove they are unchanged or establish that every file inside them is disposable.

Browser/render verification and clean dependency recreation are outstanding; keep a practical rollback or recovery copy until those checks can be performed. No legacy dependencies or episode files were removed as part of this review.
